# ⚡ Binary Tree Zigzag Level Order Traversal

> **Platform:** LeetCode 103 | **Topic:** Trees / BFS | **Technique:** Level Order with Index-Based Zigzag Fill

**Question Link:** https://leetcode.com/problems/binary-tree-zigzag-level-order-traversal/

---

## 📌 Problem Summary

Given the `root` of a binary tree, return the node values in **zigzag level order** — left to right for odd levels, right to left for even levels (alternating).

```
        3
       / \
      9  20
         / \
        15   7

Level 1 (L→R): [3]
Level 2 (R→L): [20, 9]
Level 3 (L→R): [15, 7]

Output: [[3], [20,9], [15,7]]
```

---

## 💡 Core Intuition

BFS processes nodes **always left to right** — we never change traversal order. Instead, we pre-allocate a `level` vector of size `n` and use a computed **index** to place each value:

- Normal pass (`rev=false`): place at index `i` → left to right
- Reversed pass (`rev=true`): place at index `n-i-1` → right to left

> 🪞 **Analogy:** You always read a book left to right, but on alternate pages you fill in answers from the back — the reading order never changes, only where you write.

---

## 🤔 Why Index Trick Instead of Reversing?

**Naive approach:** collect values normally, then call `reverse()` on alternate levels.
- Extra O(N) operation per level
- Two passes per level

**This approach:** pre-allocated vector, compute placement index directly.
- One pass per level ✅
- No post-processing ✅

```cpp
vector<int> level(n);         // pre-allocated, size n

int idx = rev ? (n-i-1) : i;  // computed index
level[idx] = node->val;        // place directly at correct position
```

---

## 🤔 Why `vector<int> level(n)` Instead of `push_back`?

With `push_back`, you always append to the end — you can't control **which index** a value lands at. Pre-allocating size `n` lets you use `level[idx] = val` to write at any position directly.

```
n=3, rev=true

i=0 → idx = 3-0-1 = 2 → level[2] = node0.val
i=1 → idx = 3-1-1 = 1 → level[1] = node1.val
i=2 → idx = 3-2-1 = 0 → level[0] = node2.val

Result: [node2, node1, node0] → reversed ✅
```

---

## 🪜 Algorithm Steps

1. 🏁 Push `root` into queue, `rev = false`
2. 🔁 While queue not empty:
   - Snapshot `n = q.size()`
   - Pre-allocate `level(n)`
   - 🔁 For `i = 0` to `n-1`:
     - Pop node
     - Compute `idx = rev ? (n-i-1) : i`
     - `level[idx] = node->val`
     - Push children
   - Toggle `rev = !rev`
   - Push `level` to `ans`
3. 📤 Return `ans`

## 💻 Full C++ Solution

```cpp
class Solution {
public:
    vector<vector<int>> zigzagLevelOrder(TreeNode* root) {
        vector<vector<int>> ans;
        if (!root) return ans;

        bool rev = false;
        queue<TreeNode*> q;
        q.push(root);

        while (!q.empty()) {
            int n = q.size();
            vector<int> level(n);         // pre-allocated, not push_back

            for (int i = 0; i < n; i++) {
                TreeNode* node = q.front();
                q.pop();

                int idx = rev ? (n - i - 1) : i;   // zigzag index
                level[idx] = node->val;

                if (node->left)  q.push(node->left);
                if (node->right) q.push(node->right);
            }

            rev = !rev;               // toggle direction for next level
            ans.push_back(level);
        }

        return ans;
    }
};
```

## 📊 Complexity Analysis

| Metric | Complexity | Reason |
|--------|-----------|--------|
| ⏱️ **Time** | O(N) | Every node processed exactly once, O(1) index computation |
| 🧠 **Space** | O(W) | Queue holds at most one full level; W = max width |

> 📝 Compared to the reverse-based approach which is also O(N) but with larger constant due to `reverse()` calls — this approach is cleaner and avoids extra passes.

## ✅ Key Takeaways

| # | Insight |
|---|---------|
| 1 | **BFS order never changes** — only the placement index changes |
| 2 | **`vector<int> level(n)`** pre-allocation enables random index writes |
| 3 | **`idx = rev ? (n-i-1) : i`** — the entire zigzag logic in one line |
| 4 | **`rev = !rev`** at end of each level — toggle after pushing to `ans` |
| 5 | Children always pushed **left then right** — traversal order unchanged |

---

## ⚠️ Common Mistakes

- ❌ **`push_back` instead of pre-allocated vector** → can't place at arbitrary index
- ❌ **Toggling `rev` before computing index** → wrong direction on first level
- ❌ **Reversing `push` order of children** → changes BFS order, breaks future levels
- ❌ **`rev ? i : (n-i-1)`** — flipped condition → reverses which levels go which direction

## 🔁 Index Formula Visualized

```
n = 4, rev = false (left to right):
  i=0 → idx=0  i=1 → idx=1  i=2 → idx=2  i=3 → idx=3
  level: [a, b, c, d]  ← normal order

n = 4, rev = true (right to left):
  i=0 → idx=3  i=1 → idx=2  i=2 → idx=1  i=3 → idx=0
  level: [d, c, b, a]  ← reversed order

Formula: idx = n - i - 1
  i=0 → n-0-1 = n-1  (last slot)
  i=1 → n-1-1 = n-2
  ...
  i=n-1 → n-(n-1)-1 = 0  (first slot)
```

## 🆚 Two Approaches Compared

| Feature | Index Trick (this) | Reverse After Collection |
|---------|-------------------|--------------------------|
| Extra pass | ❌ None | ✅ `reverse()` per alt level |
| Vector type | Pre-allocated `vector(n)` | `push_back` then reverse |
| Code clarity | Slightly more clever | More intuitive |
| Time complexity | O(N) — no extra work | O(N) — with constant overhead |
| Space | Same | Same |
