# 🎨 Is Graph Bipartite? — BFS (2-Coloring)

> **Platform:** LeetCode 785 | **Topic:** Graphs | **Technique:** BFS 2-Coloring — Level-by-Level Color Assignment

**Question Link:** https://leetcode.com/problems/is-graph-bipartite/

---

## 📌 Problem Summary

Given an undirected graph as an adjacency list, return `true` if the graph is **bipartite** — nodes can be split into two groups such that every edge connects nodes from *different* groups.

```
graph = [[1,3],[0,2],[1,3],[0,2]]   → true  (square: alternates 0-1-0-1)
graph = [[1,2,3],[0,2],[0,1,3],[0,2]] → false (triangle: odd cycle)
```

> 📝 You already have the DFS version in previous notes. This is the **BFS variant** — same logic, iterative queue instead of recursion.

---

## 💡 Core Intuition

Try to **2-color** the graph using BFS. Assign a color to the start node, then assign the opposite color to all its neighbors, their neighbors, and so on. If any neighbor already has the **same color** as the current node → conflict → not bipartite.

> 🌊 **BFS advantage:** Iterative — no recursion stack overflow risk for large graphs.

---

## 🔁 Key Difference From DFS Version

| Feature | DFS (previous notes) | BFS (this) |
|---------|---------------------|------------|
| Traversal | Recursive call stack | Iterative queue |
| Color passing | `currColor` parameter | `1 - color[u]` at assignment |
| Color when? | On DFS entry | When pushed to queue |
| Conflict check | `color[v] == color[curr]` | `color[v] == color[u]` |
| Stack overflow? | ✅ Risk | ❌ Safe |

**Critical difference:** In BFS, you assign color to neighbor `v` **when pushing to queue**, not when popping. This ensures no node is pushed twice with conflicting colors.

---

## 🤔 Why `color[v] = 1 - color[u]`?

```
color[u] = 0 → 1 - 0 = 1  (assign opposite)
color[u] = 1 → 1 - 1 = 0  (assign opposite)

BFS processes level by level:
  Level 0 (start): color = 1
  Level 1 (neighbors): color = 0
  Level 2: color = 1
  ...alternates with each BFS level ✅
```

---

## 🪜 Algorithm Steps

**`isBipartite`:**
1. `color[V] = -1` (all uncolored)
2. Outer loop: for each uncolored node `i`, call `bfs(graph, i, color, 1)`
3. If any BFS returns `false` → not bipartite

**`bfs`:**
1. Push `curr` to queue, assign `color[curr] = currColor`
2. While queue not empty:
   - Pop `u`
   - For each neighbor `v`:
     - `color[v] == color[u]` → **conflict → return false**
     - `color[v] == -1` → assign `1 - color[u]`, push to queue

## 🧩 Dry Run — Bipartite (Square)

```
graph = [[1,3],[0,2],[1,3],[0,2]]
color = [-1,-1,-1,-1]

BFS(0, startColor=1):
  push 0, color[0]=1
  queue=[0]

  pop 0: neighbors=[1,3]
    v=1: color[1]==-1 → color[1]=0, push 1
    v=3: color[3]==-1 → color[3]=0, push 3
  queue=[1,3]

  pop 1: neighbors=[0,2]
    v=0: color[0]=1 ≠ color[1]=0 → skip
    v=2: color[2]==-1 → color[2]=1, push 2
  queue=[3,2]

  pop 3: neighbors=[0,2]
    v=0: color[0]=1 ≠ color[3]=0 → skip
    v=2: color[2]=1 ≠ color[3]=0 → skip
  queue=[2]

  pop 2: neighbors=[1,3]
    v=1: color[1]=0 ≠ color[2]=1 → skip
    v=3: color[3]=0 ≠ color[2]=1 → skip
  queue=[]

return true ✅
color = [1,0,1,0] → Set A={0,2}, Set B={1,3}
```

## 🧩 Dry Run — Not Bipartite (Triangle)

```
  push 0, color[0]=1

    v=1: color[1]==-1 → color[1]=0, push 1
    v=2: color[2]==-1 → color[2]=0, push 2
  queue=[1,2]

    v=2: color[2]=0 == color[1]=0 → return false ❌

```

## 💻 Full C++ Solution

```cpp
class Solution {
public:
    bool isBipartite(vector<vector<int>>& graph) {
        int V = graph.size();
        vector<int> color(V, -1);

        for (int i = 0; i < V; i++) {
            if (color[i] == -1) {
                if (!bfs(graph, i, color, 1)) return false;
            }
        }

        return true;
    }

    bool bfs(vector<vector<int>>& graph, int curr,
             vector<int>& color, int currColor) {
        queue<int> q;
        q.push(curr);
        color[curr] = currColor;

        while (!q.empty()) {
            int u = q.front();
            q.pop();

            for (int v : graph[u]) {
                if (color[v] == color[u]) return false;   // conflict!

                if (color[v] == -1) {
                    color[v] = 1 - color[u];              // opposite color
                    q.push(v);
                }
            }
        }
        return true;
    }
};
```

## ✅ Key Takeaways

| # | Insight |
|---|---------|
| 1 | **Color on push, not pop** — assign `color[v]` before `q.push(v)` to prevent duplicate pushes |
| 2 | **Conflict check before `-1` check** — already-colored conflicting nodes must be caught |
| 3 | **Outer loop** — handles disconnected components |
| 4 | **`currColor` param** — matches DFS signature, though `0` would work too (just convention) |
| 5 | `color[v] = 1 - color[u]` — reads color from the popped node `u`, not the passed parameter |

---

## ⚠️ Common Mistakes

- ❌ **`color[v] = 1 - currColor` (parameter) instead of `1 - color[u]`** — `currColor` is only used to color `curr` at the start; inside the loop, use the popped node's actual color
- ❌ **Color on pop instead of push** → same node can be pushed multiple times, causing false conflicts
- ❌ **No outer loop** → disconnected components ignored
- ❌ **Skipping conflict check for already-colored nodes** → bipartite violation missed

---

## 🔁 Color on Push vs Color on Pop — Critical Detail

```cpp
// ✅ Color on PUSH (correct — your code)
if (color[v] == -1) {
    color[v] = 1 - color[u];   // colored immediately
    q.push(v);                  // pushed only once (already colored)
}

// ❌ Color on POP (wrong)
if (color[v] == -1) {
    q.push(v);                  // pushed without coloring
}
// ... later when popped:
color[curr] = 1 - color[parent]; // but parent info is lost!
// Also: v may be pushed multiple times from different neighbors
```

Coloring on push ensures:
1. Each node enters the queue **exactly once**
2. The parent color (`color[u]`) is still available when assigning

---

## 🔁 Why `currColor` Param Is Slightly Redundant in BFS

```cpp
// In DFS: currColor is essential — each recursive call has its own context
bool dfs(graph, curr, color, currColor):
    color[curr] = currColor   ← needed since DFS doesn't have parent easily

// In BFS: currColor is only used once at the start
bool bfs(graph, curr, color, currColor):
    color[curr] = currColor   ← colors the seed node
    // All other nodes colored via: color[v] = 1 - color[u]
    // currColor never used again inside the while loop

// Simpler BFS signature (no currColor param needed):
bool bfs(graph, curr, color):
    color[curr] = 0           ← just use 0 as start color
    // result is identical — two sets are just labeled differently
```

Your code is correct — the param just matches the DFS signature for consistency.
